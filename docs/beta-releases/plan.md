# Beta releases

## Verdict and recommendation

- **Feasible with changes. Recommended: (e), the owner's existing BB tracks `main` as a manually updated canary; everyone else stays on stable semver tags.** No second BB, second plugin id, Settings channel switch or bb-core work is needed. Branch updates use commit SHA, not package-version ordering. [H8] [H9]

The owner's live data and agent activity are exposed to unreleased code. Require migration/recovery gates below; use an isolated BB when a change fails them. A seamless, reversible Settings channel switch still needs bb-core support. [H1] [H2] [H10]

## 2. What this host supports

- **[V/R] Supported selectors, not named release channels:** `bb plugin install --help` accepts `git:<url>[@<ref|semver-range>]`, npm versions and paths. `bb guide plugins`, “Updates and pinning”/“Git semver ranges”, documents exact Git tags/commits and npm versions as pinned; branches/default branches, Git ranges and npm dist-tags/ranges track updates. Stable Git ranges exclude prereleases. Tags are checked against their recorded commits; never move a published tag. [H3]
- **Owner's branch updates [R]:** `@main` selects a branch; `#main` is not a ref selector. The resolver compares remote commit SHA to installed SHA, so equal package versions still update. Use CRW's Update now or `bb plugin update code-review-workspace`; `reload` only restarts current code. Updates replace code/registration without deleting settings/secrets/KV/schedules, unlike the one-time removal. Confirm the resolved SHA with `bb plugin source`; no `git pull` inside managed cache. Auto-application is CRW's existing optional idle updater, not automatic branch tracking. [H8] [H9] [H6] (`src/plugin-updates.ts:60–86,94–102`; `bb plugin reload --help`).
- **[V/R] The reinstall problem is real, but not universal:** managed reinstall/source replacement is refused. BB source throws `plugin id "${pluginId}" is already installed from ${existing.source}; remove it first`; matching managed-source reinstall is refused too. **Only direct path → direct path relocation is exempt** and keeps settings/secrets/schedules. Managed Git → path is not that exemption. `bb plugin remove --help` explicitly deletes settings, secrets and schedules, including CRW's Postgres password. [H1]
- **[V/R] Missing managed-source replacement:** `bb plugin update --help` exposes only id/`--all`, not a source, ref, version or downgrade. Current SDK `applyUpdate({ pluginId })`/`checkUpdates` have no channel or candidate argument; install still hits the identity checks. [H1] [H2]
- **Boundary:** CRW can publish beta tags, show instructions/version warnings, gate activity, or run under another id. It cannot implement **supported, config-preserving managed-source retargeting** with the present API. Full-trust code could edit host internals or remove/reinstall itself, but that is an unsafe replacement installer, not a suitable design. A proper Settings opt-in needs a bb-core source-replacement/selector API and CLI first. [H1] [H2]
- **[R] Existing developer escape hatch:** a plugin already installed from a local path can change code there and reload without deleting config (`bb guide plugins`). Use a durable checkout, not an ephemeral worktree. This does not convert this owner's Git install, and does not undo migrations. [H1]

## 3. Options: safety / effort / owner action

- **(e) Owner tracks `main` — recommended.** Lowest setup/maintenance; use normal CRW and the existing BB. One-time backed-up source switch, then manual `bb plugin update code-review-workspace` after reviewing the incoming commit. Owner bears canary failures; stable-range users see nothing until a stable tag is published. Use this only for additive, rehearsed migrations with a current restore point. No beta tag is required for branch tracking; optional immutable beta tags identify tested checkpoints. [H1] [H3] [H9]
- **(a) Settings opt-in + beta tag/channel.** Convenient long-term UX, **high cross-repo effort**: source selector belongs to BB, not a CRW preference. Requires bb-core prepare/confirm/replace API, retained config and local snapshot, explicit downgrade semantics, then CRW Settings integration using its activity guard. Beta opt-in and auto-apply must remain separate, both off by default. A `beta` GitHub release label alone cannot implement selection or database recovery. [H1] [H2] [H3]
- **(b) Separate `code-review-workspace-beta` id alongside stable.** Feasible in CRW, medium/high maintenance; owner installs/configures a second plugin. Package name determines id [H7]; BB routes/storage/settings are namespaced (`bb guide plugins`, “Plugin commands”). Relative `review` paths can coexist as `/plugins/<id>/review/...` (`src/review-command.ts:74`; `lib/review-session.tsx:8–24`). But merely renaming the package is insufficient: distinguish `bb review`/skills (`server.ts:97–101,374–378`), hardcoded icon ids (`app.tsx:74,85,96`), draft-recovery keys (`lib/draft-recovery.ts:15`) and notification identities (`src/completion-notifications.ts:28,102–107`); avoid duplicate overlays/thread actions. **Separate SQLite is automatic; Postgres is not:** default schema is still `code_review_workspace`, so require a beta database/schema and restricted role. Same-schema writers contend on the same lock (`src/storage.ts:25–28`; `src/db/pg.ts:400–409`). Never share writable review data across identities.
- **(c) Exact prerelease/ref over stable, retaining config.** Fresh install supported, **replacement of this managed install unsupported**. Seamless replacement needs the same bb-core change as (a); otherwise use the explicit backup/restore migration in §4, never edit BB's registration database. If already path-installed, checkout/build/reload preserves config, but rollback remains a data-compatibility operation. [H1] [H2]
- **(d) Isolated BB, same id — fallback.** Strongest data isolation, but more operator setup: separate BB data/endpoint, credentials, projects and a disposable database. Use for destructive/uncertain migrations or unacceptable live downtime. Track `main` or a beta-only range such as `>=1.13.0-beta.1 <1.13.0`; never reuse production's writable schema. Existing test infrastructure supports isolated BB (`docs/development.md:44–60`).
- **Not equivalent:** shipping stable-numbered code with a feature toggle still ships beta startup/migrations to everyone; focuses-off does not prevent migration (`server.ts:123–141`). A moving branch is acceptable for the deliberate canary, not a reproducible stable release: record its resolved SHA. [H9]

## 4. One-time switch: loss, backup and restoration

- **[R] Deleted by BB 0.49.0:** the installed-source registration (including its enable/source/update state), every declared host setting, the plugin's secret directory (Postgres password and HTTP token), schedules and managed code/cache. CRW re-registers schedules on load (`server.ts:119–122`), but old last/next-run bookkeeping is lost. Removal is not an update transaction with automatic undo. [H10] [H11] [H14]
- **[R] Preserved on this exact host implementation:** plugin `data.db`, export/backup files and KV rows, including `storage:owner`; removing the installed row has no KV/settings foreign-key cascade. Postgres schema/tables and external GitHub posts are untouched. CRW preferences/drafts live in its chosen Store, not the deleted six host settings; the local `plugin_updates` auto-update flag also survives. These are source findings, **not a live remove/reinstall test or a promise for future BB versions**. Back them up anyway. [H10] [H11] (`src/storage.ts:14–38,80–101`; `src/plugin-updates.ts:23–27`; `docs/operations.md:39,194–196`).
- **[R] Export limitation:** `bb plugin config code-review-workspace --json` can save schema/effective **non-secret** values, but a secret is only `{ set: true }`; no value or bulk config import is provided. Restore each non-secret value with Settings or `bb plugin config … set …`. Securely retain the password from the owner's secret manager or an operator-only backup of `<dataDir>/plugins/code-review-workspace/secrets/`; never paste it into a thread. Use Settings' password field rather than exposing it in process arguments. [H12] (`bb plugin config --help`; `docs/operations.md:67–75`).
- **Backup inventory:** all six host settings (`storageBackend`, `postgresUrl`, `postgresPassword`, `postgresSchema`, `postgresSsl`, `postgresCaPem`), current source/commit and enabled state; consistent SQLite and KV/host-state backup; separate Postgres restore point. Back up secrets privately off-server, encrypted/restricted. HTTP token consumers need the old token restored offline or a new token configured; a redacted config JSON alone cannot recover it. [H10] [H12] [H14]
- **Full-state escape hatch:** `bb server export` includes credentials/plugin secrets, writes an unencrypted 0600 archive and is gated by the existing `serverMove` experiment (`bb guide machines`). Do not enable/reconfigure it for this task. If unavailable, use the operator's normal consistent BB-state backup. There is no supported single-plugin import: whole-server recovery is a last resort affecting other BB work, not a routine config restore.
- **Restoration:** re-enter all six settings, with `storageBackend` last; for a Postgres snapshot recovery, first override `postgresSchema` (and `postgresUrl` if needed) to the restored target as specified in Phase 4, not the migrated original. Then reload and verify `state: serving`, the same reviews/preferences and `storage:owner`. Retained `postgres` ownership plus missing/default settings deliberately starts CRW in maintenance, not a new SQLite review store. Do **not** run `bb review storage migrate`: this switch changes code source, not backend ownership. Stop on missing data/marker and recover the backup instead. (`src/storage.ts:80–112`; `src/storage-cli.ts:73–80`).

## 5. Data safety and downgrade policy

- **[V/R] Focuses schema delta:** both backends grow from **40 to 43 migrations**, ids **40–42**: `focus_threads`, `focus_findings`, `review_preferences.focuses`. Read-only array comparison against `v1.12.1` verified the first 40 statement strings are unchanged. SQL changes are additive (`src/store.ts:803–820`; `src/db/pg-migrations.ts:86–95`), but additive SQL alone does not prove behavioral downgrade compatibility.
- **[R] Migration timing:** SQLite migrates while opening the Store, before serving; Postgres locks its schema's writer, checks the migration ledger exists, then migrates in its storage service (`server.ts:123–141`). SQLite delegates to `bb.storage.migrate`; Postgres applies missing statements in one transaction under an advisory lock and rejects changed hashes at known indexes (`src/store.ts:817–825`; `src/db/pg-migrations.ts:105–131`). No down migrations exist in either list.
- **[V/R] No general “newer schema” startup guard:** both migration runners iterate only their known statements; extra applied ids do not fail startup. [H4] An in-memory execution of the **extracted SDK 0.6.132 SQLite helper** accepted an older one-statement list after applying a two-statement list; ledger rows stayed at 2. This verifies the helper, not a live CRW downgrade. Postgres behavior was read, not executed (`src/db/pg-migrations.ts:118–129`).
- **[R] A partial guard already exists, only for storage copying:** `src/storage-copy.ts:145–172` rejects unknown/newer migration ids. It is not called on normal Store startup. Focus preferences deliberately occupy a separate column; `src/focus-groundwork.test.ts:51–64` simulates an old settings save preserving it. That test was read, not run, and does not certify older runtime behavior, draft rewrites, deletion/merge operations or running focus threads.
- **Practical downgrade assessment [R]: structurally favorable, not certified safe.** The two new tables and nullable column leave 1.12.1's named SQL queries valid; its preferences save names only `value`/`knobs` and leaves `focuses` intact, and lifecycle updates merge raw JSON, preserving unknown fields ([stable Store:905–923,961–974][stable-store]; `src/focus-groundwork.test.ts:51–64`). But 1.12.1 does not manage focus workers/findings; its review deletion omits their tables and its posting code does not render focus labels ([stable Store:986–989][stable-delete], [table list:1783–1788][stable-tables]; [stable draft:29–34][stable-draft]). Therefore additive SQL is not permission to run old code on live canary data, especially with active agents. No full same-data downgrade was executed.
- **Small guard: worth adding.** Before migrations/Store writes, reject unknown applied migration ids and changed known hashes on both backends; missing trailing ids remain an upgrade. Keep it CRW-local and test a future ledger without mutating it. It prevents accidental old/new-canary schema mismatches, but **cannot retrofit protection into released 1.12.1**, detect every serialized-data change or undo a migration. A post-migration Postgres activation rollback may then refuse the old guarded build; availability requires forward repair or restore, not bypassing the guard. [H4] [H6]
- **Canary policy:** append-only migration history, additive/backward-compatible schema **and** serialized-data changes; back up before every schema-changing update. Preferred repair is a **new forward fix/revert commit on `main` that retains all migration statements and compatible storage code**. Do not blindly revert a merge and remove migrations 40–42. To return to actual 1.12.1, stop workers and restore a consistent pre-focus data/config snapshot before changing source; for Postgres, use a new schema and point the restored config at it before reloading, following Phase 4. Never reload with settings that still name the migrated original schema; later edits are lost unless separately salvaged. If this risk is unacceptable or migration is destructive, use the isolated fallback.
- **Snapshot boundary:** BB's managed update snapshots local `data.db`, secrets and host-side plugin state, and rolls back activation errors during its 30-second check; **Postgres is outside it**, and later correctness bugs are not activation failures. [H5] [H6] `docs/operations.md:148–152` requires SQLite backup API/`VACUUM INTO`, not copying an active WAL database, and separate Postgres backup. If restoring a whole-database/cluster backup, restore it separately and extract CRW data into the new schema specified in Phase 4: never rewind the shared CNPG cluster and other applications to roll back one beta. Treat GitOps backups as configured, not proven restorable.

### Phase 4 — broken `main`: containment and recovery

- **First switch:** remove/install has no previous installation to roll back to. If it fails, restore the recovery bundle and reinstall the recorded known-good ref, with the pre-focus database if migrations already ran; for Postgres, follow the restored-target/config procedure below rather than restoring settings that name the migrated original schema. The automatic protections below apply to **later managed updates**, not this outage.
- **Before activation (fetch/engine/build failure):** previous code/config/data stay installed; fix `main`, then retry the normal update. **Time:** no replacement downtime from this failure; retry still needs fetch/build. [H13]
- **Activation error detected in the default 30-second window:** BB restores the previous registration/local snapshot and reloads it. **Time:** detection within that window plus recovery/reload, not a 30-second end-to-end SLA. Postgres remains migrated. CRW Postgres initialization can report needs-configuration/retry rather than host error, so not every broken startup triggers automatic rollback. [H5] [H6] [H15] (`src/storage.ts:180–215`).
- **Late/UI/behavioral fault:** disable CRW through core CLI/Settings, stop its independent workers and block posting. Default recovery is a new **forward repair or selective revert commit** on `main`, retaining migrations 40–42, the guard and compatible storage behavior; update/re-enable and verify (enabling after an update done while disabled is manual recovery, not a new protected update window). No source switch, config deletion or database restore is needed **if data is intact and the repair is compatible**. A successful update's snapshot is cleaned up, so do not assume a later one-command rollback exists. [H9] [H15]
- **Data corruption or return to 1.12.1:** disable/stop workers and preserve current state for salvage. Restore the pre-change SQLite/host state as applicable. For Postgres, restore the CRW snapshot into a new schema, e.g. `code_review_workspace_restore_<date>`, in CRW's database; keep the original schema untouched for salvage. Repeat the backed-up remove/install/config restore with an exact known-good ref, but set `postgresSchema` to the restored schema (and `postgresUrl` if restored to another database) before reloading. Never reload with settings that still name the migrated original schema. `storage:owner` records only the backend, `"postgres"`, not the schema, so this does not trip the ownership check (`src/storage.ts:84–112`); the writer lock is per schema. Never rewind the shared CNPG cluster. If code changes dropped schema compatibility, do not enable old code on newer data merely because it starts.
- **Recovery speed:** forward repair is one commit + fetch/build/reload; aim for minutes only after rehearsal. Database restore time is unknown until measured and may be much longer; use the rehearsal's measured recovery time/data-loss window as the go/no-go gate. No speed was measured in this research. If downtime or possible loss of post-backup edits is unacceptable, use isolated BB.

Require external-database recovery acknowledgement; never claim a Postgres snapshot exists. Test cancellation, activation failure, retained credentials and downgrade refusal.
- **Then CRW:** Settings “Receive beta updates” invokes that host flow under the existing idle guard; do not store a disconnected boolean. Display selected source/resolved version/schema risk, and keep auto-apply independent. Returning to stable is a confirmed restore/compatibility operation, not silently changing a checkbox. [H1] [H2] [H5]

## Open questions — recommended answers

- **How much canary downtime/data loss is acceptable? Recommended: owner specifies a recovery-time target and backup-loss window, demonstrated before the switch.** Otherwise isolated BB; configured backups alone do not prove recovery.
- **Where will the deleted password/config be recovered from? Recommended: owner's secret manager plus private consistent BB-state/SQLite and CRW Postgres backups.** Verify recoverability without exposing credentials in chat; redacted config JSON is insufficient.
- **Automatic `main` updates? Recommended: off initially; manual acceptance of each installed SHA.** Keep a quiet merge window during acceptance; upgrade schema only after a fresh restore point.
- **Public beta tags? Recommended: optional immutable `v1.13.0-beta.N` checkpoint; no beta marketplace or Settings channel work.** Focuses is the first canary beta; only owner-approved commits become stable tags.
