# Code Review Workspace

A code review workspace for [BB](https://getbb.app). Read a GitHub pull request or local Git change as an agent-authored walkthrough in chapters, inspect the diff, ask an assistant about it, and prepare and submit your review in one place.

It's built for understanding a change well enough to approve it, often one an agent wrote: a guided reading of every file, draft comments and a verdict you edit, whose turn each review is, and a re-review that checks your earlier feedback against what changed. If you want a list of an agent's findings to post one by one, the [Code Review](https://github.com/robennals/bb-plugins/tree/HEAD/plugins/code-review) plugin does that.

Formerly **Guided Review**: coming from it? See [Moving from Guided Review](#moving-from-guided-review).

**v0.9.0.** Each reviewer uses their own BB installation and GitHub identity. On a shared BB server, credentials, settings, and saved reviews are shared.

## Install and first run

You need **BB 0.45+ (plugin SDK 0.6.14+) with Node 24+**, a configured BB agent provider, and `git` and GitHub CLI (`gh`) on the **machine running BB**. GitHub features support github.com. No npm or build step is needed.

Install Code Review Workspace from its Git repository; the range follows compatible 0.9.x releases:

```sh
bb plugin install git:github.com/AndrewBird81/bb-plugin-code-review-workspace@^0.9.0
```

1. Open **Code Review Workspace**. With no reviews yet, **All reviews** checks your setup and says how to start; you can revisit it in **Settings → Ready to review**.
2. Sign in on the BB server with `gh auth login --hostname github.com`. Check the account displayed in Code Review Workspace and its access to the repository. No token is pasted into the plugin.
3. Paste a GitHub PR link into the box on **All reviews** and choose **Review**, or press Enter. Your BB agent writes the chaptered guide using its normal usage allowance. When the guide is ready, the review assistant reviews the change, adds draft comments, and writes a review summary with the verdict it suggests. On PRs from outside your repository's members and collaborators, or whose branch is in someone else's fork, agents wait for your click (see [Data and access](#data-and-access)).
4. The review opens on its Overview; **Start reading** takes you through the chapters. Edit or remove the assistant's draft comments and summary, or ask it to change them, add your own, or ask the assistant about a file or selection.
5. Open **Finish review**, choose a verdict, and **Submit to GitHub**. Drafting, generating, and the assistant never submit a review. Replies and resolve actions on existing GitHub threads are separate, immediate actions.

GitHub account switching affects `gh` on the BB server. Environment tokens can override saved-account selection; the plugin reports when a switch has not taken effect. Review submissions verify the displayed account and use its credential for the entire request.

## Updates

Open **Settings → Plugin updates** to check for a compatible release, read its release notes, and choose **Update now**. Save or discard settings edits and close other Code Review Workspace pages first. BB installs the latest compatible release available at installation time; it may advance beyond the version shown by an earlier check.

**Automatic updates are off by default.** If enabled, the plugin checks hourly after five idle minutes and waits until all Code Review Workspace and Settings pages are closed, with no generation, save, or submission in progress. Assistant conversations run in BB and continue across plugin updates. Reviews, drafts, private notes, conversations, and preferences remain in BB. Failed checks are visible and retried later; BB handles failed-install rollback.

Installs from a Git range, such as `^0.9.0`, follow its compatible releases (0.9.x). You can also update with `bb plugin update code-review-workspace`; close the plugin’s pages first, since BB’s external update command does not use the in-plugin activity guard. Local directories and exact tags are pinned and do not receive automatic updates. Changing a local installation to a Git source is a separate migration: this BB version requires removing the old source first, which can clear plugin data. Do not remove an existing installation just to obtain updates; keep its data and arrange a backup/migration with the BB operator. Fresh installs from a Git range are ready for normal updates.

An interrupted browser connection can leave an editing session protected. If the updater still asks you to close pages after they are all closed, save any work elsewhere and reload the plugin through BB. Editing sessions intentionally never expire while a laptop might still hold unsaved text.

## Moving from Guided Review

Until 0.9.0 this plugin was Guided Review, with the id `guided-review`. BB keeps a plugin's data under its id, so Code Review Workspace is a new install beside it, not an update. The first time it starts, it copies in Guided Review's reviews, guides, drafts, private notes, and settings, as long as it has none of its own yet, and the review assistant's conversations carry on with Code Review Workspace's tools. Don't update Guided Review to 0.9.0: install Code Review Workspace beside it.

1. Submit or save any comment you're typing, and close Guided Review's pages.
2. `bb plugin disable guided-review`. It keeps its data; disabling it stops both plugins following your PRs and starting agents at once, and both registering `bb review`.
3. `bb plugin install git:github.com/AndrewBird81/bb-plugin-code-review-workspace@^0.9.0`
4. Open **Code Review Workspace** and check your reviews are there. `bb plugin logs code-review-workspace` says "Brought in the reviews from guided-review" when it copied them.
5. Then `bb plugin remove guided-review`, which can delete its data. Until then, you can go back by removing Code Review Workspace and enabling Guided Review.

What doesn't carry over: the small state kept outside the plugin's database. An alert already in Needs You stays Guided Review's, and one still waiting to be sent is dropped; what happened on your PRs before the move counts as history, as when a review starts being followed, so it doesn't make a review your turn again. The copy runs once, at Code Review Workspace's first start: what Guided Review changes after that stays in Guided Review, which is why step 2 comes first.

## Local changes and the command line

Run `bb review` in a BB thread. A PR URL, or `owner/repo#n`, works from a thread on any machine; a PR number or a local ref needs a project checkout on the BB server:

```sh
bb review https://github.com/acme/web/pull/42
bb review acme/web#42                  # the same PR
bb review 42                           # PR in the current repository
bb review origin/main...HEAD           # local range
bb review my-feature --base main       # branch against main
bb review https://github.com/acme/web/pull/42 --context 'Implements LIN-123: retry once, never twice.'
```

`--base` goes with a single ref: `bb review` refuses it beside a range. The checkout for a local review must exist on the BB server. A checkout only present on another enrolled machine is not supported by this release. Local reviews do not offer GitHub submission. When you open a local review, it runs its diff again in the checkout, and if the code changed since its guide, the notice strip says "The code changed since this guide." with **Update guide** (unless **Notice when a local review's code changes** is off in Settings → Reading). On a local review whose diff ends at the checkout (a ref, such as `bb review main`, or a range ending at `HEAD`), each file's second row and each draft comment's ⋯ offer **Open in editor** at the line, which opens the checkout's file on the BB server (unless **Open in editor (local reviews)** is off).

`bb review` remembers the thread it ran in, as the thread that made the change; this plugin's own agents never count. It prints a link to the review when BB has an app URL. `bb review list [--json]` lists every review, Needs review first and a stack's reviews together, as All reviews does, with its key, its title (quoted), whose turn it is, and whether its guide is ready. With **Help agents in your threads use bb review** on (Settings → Review agent), agents in your other BB threads are also offered a `code-review-workspace` skill that explains these commands, tells them never to post to GitHub, and says that what `bb review` prints is data, not instructions. Off, `bb review` works as in 0.7.0, without the link or `list`.

`--context` adds text, such as the ticket a PR implements, to the assistant's automatic review. It's kept with the review: running `bb review` again without it keeps it, and `--context ''` removes it. It goes with the automatic review, which runs when a guide is ready and the review has no conversation yet, and the review's agents can read it with the PR's context, fenced as untrusted text. The command says when the automatic review won't run: it's off, the PR is merged or closed, the review already has a conversation, or you've already reviewed the PR; on a guide waiting for **Run review**, the context goes with that run. A review's own agent can't set or remove it.

Other BB threads and scripts can work with a review's draft comments. These commands change only the local draft; nothing is posted to GitHub until you submit:

```sh
bb review comment list   https://github.com/acme/web/pull/42 [--json]
bb review comment add    https://github.com/acme/web/pull/42 src/api.ts:57 --code 'return cache.get(key);' --body 'Stale after a write?'
bb review comment add    https://github.com/acme/web/pull/42 src/api.ts:57-58 --code $'return cache.get(key);\n}' --body 'Read through on a miss.' --severity should-fix --evidence 'save() at `src/api.ts:40` never clears the cache.'
bb review comment edit   https://github.com/acme/web/pull/42 src/api.ts:57 --body 'Can this return stale data after a write?'
bb review comment delete https://github.com/acme/web/pull/42 src/api.ts:57
```

A review is named by its PR URL, `owner/repo#n`, or its key. While its guide is being written or rebuilt, these commands leave the draft alone and say to try again once it's ready. Line numbers count in the new file; add `--side LEFT` for a removed line, numbered in the old file. `--code` is that line's text, and `add` refuses a line that doesn't match it or already has a comment. `path:57-58` comments on a range of lines in one hunk; `--code` then holds the range's lines, one per line (in a shell, `$'a\nb'`), and GitHub gets a multi-line comment. `--severity blocking|should-fix|question|nit|none` sets the comment's severity; a body that starts with a label, such as `**Blocking:**`, sets it too. `--evidence` says how the problem was confirmed, what was read or run, with file:line, in up to 600 characters; the card folds it under **How the agent checked**, and it's never posted. `--pre-existing` marks a problem in code the PR didn't change (see [Comments and Finish review](#comments-and-finish-review)); `edit` without it keeps the comment's mark. `--body` takes up to 65,000 characters, GitHub's limit. `list` shows each comment's range and severity. Comments added this way show as added by an agent. A review's own agent, its assistant or guide writer, can use these commands only on its own review.

The review summary works the same way. `--suggest` marks the verdict you'd suggest; the reviewer still picks it. A summary the reviewer wrote is refused, unless they asked on it:

```sh
bb review summary https://github.com/acme/web/pull/42 [--json]
bb review summary https://github.com/acme/web/pull/42 --body 'One blocker: the retry can double-charge (`src/pay.ts:88`).' --suggest REQUEST_CHANGES
```

## What the review workspace includes

- The code first. A review's commands sit in BB's **Code Review Workspace** title bar: **Comments**, with a badge counting what needs you; **Ask agent**; **Finish review**, with the verdict and how many comments will be sent; **Review actions** (⋯); and **Full screen**. Over the code is one 44px band: the chapters toggle and **Find in review** while the chapters aren't docked (docked, they head the chapters), **‹ All reviews**, the chapter you're on with its progress ring, the compare select on a re-review, **Fold comments**, and **Diff options**. **Full screen** covers BB's bars, on an iPhone too; the band then ends with the review's commands, and toasts, **Undo** among them, show over it. A phone has no band: see [Phone and iPad](#phone-and-ipad).
- The chapters and the side panel (Comments, Finish review, or the review agent) dock beside the code while it keeps at least 560px; otherwise they slide over it, and Esc, a tap on the code, ✕, or choosing something closes them. The panel docks narrower, down to 320px, before it covers the code. With no room for both, the chapters wait while the panel is docked and dock again when it closes. Drag the line between a side and the code to resize it; double-click or double-tap it for the default width. Widths are kept for every review.
- A review opens on its **Overview** the first time, and whenever it comes back to you (unless **Open on the Overview when a review comes back** is off in Settings → Reading): the title, which opens the PR; the author, repository, and branches; the changed lines to read with a rough reading time ("about 4 h to read", in days past 24 hours; about 400 lines an hour, without lockfiles and generated files); a status line in All reviews' words (whose turn, **Blocks merge**, your feedback's progress, checks); your earlier reviews and the stack; then **Start reading**, **Continue** where you were, or **Review changes** at the first chapter that changed since your review, with **Snooze** while it's your turn. Below come **Since your review**; **What and why**, which ends with a line when the PR changes a file the agents read for the repo's rules ("This PR changes CLAUDE.md, which the agents read; they use the base version."); **Start here**, the guide's one to three riskiest lines, each opening its line, a removed line on the diff's old side; **Requirements · 3 of 4 covered**, what the PR's description and linked tickets ask for and whether the diff does it, with evidence and a link to the line (Settings → Reading can hide it); failing and pending checks with **View check**, and **Ask agent** on a failing GitHub Actions check, which reads the end of its failed log and quotes it into the agent's box, unsent; and the chapters. When the review came back to you, Comments opens on what needs you where it can sit beside the code in BB's pane, or a "3 need you" pill offers it until you scroll. Otherwise a review reopens where you left it, scroll position included.
- Ordered chapters with intent, file summaries, risk labels, and changed-line counts. The chapters list, **Chapters | All files**, starts with the Overview, which says where the review stands, then a bar of viewed files with **Next unviewed**, then each chapter, with its files named by the shortest end of their path no other file shares, and the current file kept in view. **Skip to code** comes first for the keyboard. On a phone the switch heads the chapters sheet, and the files viewed share the bar's row. Each chapter opens on an intro: one line ("Chapter 1 of 3 · Medium risk · 3 files · 27 lines · 0 of 3 viewed"), its title, and its overview; medium- and high-risk chapters add **What to verify**, one to three things to check, ending with **Dig deeper**, which asks the review agent for a closer pass over that chapter at high effort, with at most 5 comments, arriving in Comments. On a phone the overview shows three lines until **More**, and **What to verify · 2 ›** is one line that opens the list. Every changed file appears in one chapter, except that a guide can split a file mixing unrelated changes: each chapter then shows only its hunks, with an "Also in" note. Files the guide leaves unplaced appear in a last **Other files** chapter. A chapter ends with what you've viewed and commented, **Mark viewed and continue**, and **Next: …**; the last one offers **Mark viewed and finish** or **Finish review**, and names the files you haven't viewed yet.
- **Mark chapter viewed** works on any chapter: on the open chapter's card in the chapters list, from the ✓ another chapter shows on hover or focus with a mouse, with `⇧V`, or at the chapter's end. It, **Mark viewed and continue**, and **Mark viewed and finish** leave a file split across chapters for the last chapter holding its hunks, and the toast says where it continues ("a.ts continues in Caching."); the file's own **Viewed** still marks all of it. **Undo** in its toast puts every file back as it was. A mark that didn't save is put back, and says so.
- Syntax-highlighted diffs and viewed-file tracking. Changed lines are marked + and −, not by color alone. Only a slim row sticks above each file's code: its path, "New since your review" or "Changed since your review" on a re-review, its comment count (drafts and unresolved GitHub threads), its additions and deletions, and **Viewed**. Under it, a row that scrolls away holds the guide's one-line summary, Renamed, Also in, the file's owners, "Changed since you viewed it" on a viewed file that changed again, a chip on a test file whose diff removes assertions or skips tests ("3 assertions removed · 1 test skipped"), a lockfile's packages added and removed ("+3 −1 packages") and a warning when one downloads from a host other than its registry, a warning when the file's path or added lines hold hidden bidirectional Unicode, which can make code read differently than it runs, what a file with no changed lines does ("Binary file.", "Made executable.", "New empty file.", or "GitHub didn't send this file's diff; read it on GitHub."), **Show diff**, **Expand**, **Whole file**, and on a local review that ends at the checkout **Open in editor**. Lockfiles, generated and vendored files (`vendor/`, `third_party/`, `Pods/`, protoc and Dart generated files, and what `.gitattributes` at the PR's base marks `linguist-generated` or `linguist-vendored`), and diffs over 1,500 changed lines start folded, with **Show diff** ("Large diff · 1,600 lines"), and a file folds when you mark it viewed. A file the PR adds, or moves in from a path that isn't generated, is read as code whatever its path; Settings → Reading can turn off either fold, though huge diffs still start folded. **Expand** loads the whole file, to expand around its hunks; **Whole file** shows every line. Comments still go only on lines in the diff. A file whose diff can't be drawn says "Couldn't show this file's diff." in its card, with **Try again** and, on a PR, **Open on GitHub**; the rest of the review still shows.
- **Diff options** (the sliders icon, at the band's end) holds how the code draws: **Layout**, Unified or Split (saved for every review; the diff goes unified when its pane is narrower than 960px, and says Split needs a wider pane); **Wrap long lines**; **Hide whitespace changes**, which shows whitespace-only changes as unchanged, like `git diff -w`; **GitHub threads in code** (remembered in this browser); **Collapse all** and **Expand all** for the chapter's files; and, with a mouse or trackpad, **Keyboard shortcuts**. Where the band has no room for them, it also holds **Fold comments in code** and the comparison (see [Whose turn](#whose-turn)). On a phone, and on one held sideways, it opens as a drawer from the bottom, without Layout: the diff is unified there.
- CODEOWNERS owners on each file ("Owned by …"), read from the PR's base branch as GitHub does. Files you or your teams own are marked **yours**, and the assistant is told which they are. **Code owners** in Settings → Reading hides them; the assistant still knows.
- **All files** switches the chapters list to every changed file as a folder tree, with a filter; each file shows whether it's viewed, its comments and discussions, whether it changed since your review, its kind, and its owners. **Find in review** searches every line of the diff, both sides, and the guide's text; a result opens its line in its chapter.
- Comments in the code, under their lines, as on GitHub, each with all its actions, so a whole re-review can happen in the code. With a mouse, click **+** beside a line to write one there, or select lines and choose **Comment** in the selection bar; on an iPad or phone, tap a line to select it, tap another to make a range, then choose **Comment**. Several lines make a range comment ("Lines 10–15"), sent to GitHub as a multi-line comment. **Suggest change** in the comment box inserts a suggestion block with the new lines' current text, fenced with more backticks than the lines hold, and draft cards show it as the code it would put in place. Edit or remove a comment in place; Cmd/Ctrl+Enter saves, Esc leaves the box with your text in it, and **Cancel** discards it. If a comment lands on the line while you write, the box says "This line already has a comment. Saving yours replaces it." and its button reads **Replace comment**; an edit box whose comment changed while you edited it, in another window or by an agent, says so over its new words before you replace it; one whose comment a guide update moved follows it, and one whose comment was removed meanwhile says it was moved or removed, and that saving puts yours back. A box whose line is no longer in the diff, after a reload or a guide update, moves to Comments, where you can finish it or move it to another line; so does a box on a line Since your review hides, with **Show in diff**, which shows all changes and puts the box back under its line. A draft saved or removed in one window shows in the review's other windows.
- One card for each comment, the same in the code and in Comments, that says where the comment lives, in words as well as looks: anything only in BB is dashed and says **not submitted**; a GitHub thread is solid, headed **On GitHub**, with who wrote each comment and when; a private discussion with the agent is muted, with a lock. An agent's draft can fold **How the agent checked** under its words: what it read or ran to confirm the problem, with file:line. That stays in BB; submitting never sends it. A problem in code the PR didn't change carries a **Pre-existing** badge. Images in other people's comments and the agents' words show as links ("Image: alt"), HTML comments stay hidden as on GitHub, and HTML tags other than a few that only format show as text; in code it can't be sure is code, a `<` shows as `&lt;`. See [Comments and Finish review](#comments-and-finish-review).
- Everyone's GitHub review threads under their lines, with **Reply** and **Resolve**. Resolved and outdated threads are folded; outdated threads and file comments wait in their file's fold, "Outdated (1) · File comments (1)". **GitHub threads in code** in Diff options hides them all. CI failures with annotations show on their lines too, including ones CI reports after you open the review, with **View check**, unless **CI failures in the code** is off in Settings → Reading; the Overview lists failing checks either way. A failure's note also offers **Comment**, which opens a Blocking comment at the line quoting the failure, and **Ask agent**, which quotes it into the agent's box, unsent.
- **Fold comments** (`i`, or the band's button) shrinks every comment in the code to a one-line marker, with **Show** to open one, so the code reads on its own. On a phone they start folded.
- Discussions with the assistant under a line, kept apart from its comment. **Ask agent** on a comment opens a box under it: say what's wrong or ask why, and the assistant answers there, or edits or removes the comment. **Undo** puts back its latest change. **Ask agent** in the comment box, or on selected lines, asks about the lines without adding a comment; text selected in the code, a long-press included, offers **Ask agent about selection** (unless **Ask agent about selected text** is off in Settings). Discussions stay in BB: submitting sends only the comments, and clears the discussions.
- **Comments** beside the code, one list of your draft comments and the agent's, everyone's GitHub threads, and your discussions with the agent; and **Finish review**, which gathers the summary, the verdict, and exactly what will be posted (see [Comments and Finish review](#comments-and-finish-review)).
- **Ask agent** opens the review agent beside the code. The conversation is BB’s own chat: streamed answers, stop, queued messages, approvals, attachments, and a per-message model and effort picker. The assistant can add, edit, and delete draft comments and write the summary, and the changes appear in Comments and the code as it works. Besides the diff, it reads the PR's description, linked issues, commits, failing CI, other reviewers' open threads, and the repository's AGENTS.md, CLAUDE.md, Copilot instructions, and REVIEW.md, from the PR's base, and treats all of it as untrusted. **Pop out** moves it into a movable, resizable widget, and **Dock** puts it back; on a phone it stays in its sheet. While it's popped out, **Ask agent** asks in the widget. The arrow keys move the widget from its ✦ mark, as they resize it from its corner.
- One notice strip under the band says what to know: "New commits since this guide was written." with **Update guide** (or, when a stacked PR is retargeted, "The PR's base changed from parent to main since this guide was written."), "The code changed since this guide." on a local review, a guide update that failed and why, or one waiting for its writer's machine to reconnect, what didn't run on its own and why, a GitHub account that GitHub refuses for the repository (not when GitHub just can't be reached), or "Reconnecting…" while the connection to BB is down; the review reloads once it's back. While a guide updates, its notice offers **Stop**, which keeps the guide you had. **+N** shows the rest.
- **Review actions** (⋯) lists, in the same order everywhere: **Update guide** or **Rebuild guide**, **Snooze**, **Pin**, **Archive**, **Open on GitHub**, **Keyboard shortcuts** (not on a phone), **Review settings…**, and **Delete…**.

A review is pinned to the PR snapshot it was generated from. If the PR gets new commits, or a new base, as when a stacked PR is retargeted after its parent merges, choose **Update guide** before submitting: Submit refuses a review of an older commit or base, and keeps your draft. Unsent draft comments follow their lines into the new diff, with their discussions with the agent: a comment follows its exact code, indentation included, to the nearest line holding it, and re-indented code only when the exact code is gone. A comment whose line is gone, or on code as common as `}` whose neighbouring lines changed, is marked **Older diff**: edit and save it, remove it, or **Move to summary**, which adds it to your summary as a line ("On `src/api.ts:57` (an earlier diff): …") and removes the comment, with no Undo, before submitting. Submission failures retain the draft; repeated clicks cannot submit the same draft concurrently. Unsaved summaries and comments keep a recovery copy in this browser tab, bound to their original review revision. While the guide updates, the current one stays, with your unsaved edits.

### Keyboard shortcuts

| Key | Action |
|---|---|
| j / k | Next or previous file; on the Overview, `j` starts the first chapter |
| n / p | Next or previous chapter |
| u | Next unviewed file, in any chapter |
| ] / [ | Next or previous comment or discussion, in Comments' order and filter |
| / | Find in review |
| f | All files, with the cursor in their filter |
| v | Mark the file viewed, or not, and go to the next |
| ⇧V | Mark the chapter viewed |
| t | Show or hide the chapters |
| c | Show or hide Comments |
| a | Ask agent |
| s | Finish review |
| Esc | Close what's over the code, leave full screen, or clear the lines selected |
| d | Since your review or All changes, on a re-review |
| i | Fold or unfold comments in the code |
| ⇧F | Full screen on or off |
| ? | Show these shortcuts |

They work anywhere in a review, its commands in BB's title bar and the chapters or a panel open over the code included, except while you type, or with Ctrl, Meta, or Alt held; `]` and `[` also work where AltGr or Option types them. With Caps Lock on, a letter acts as its lower case: Caps Lock V marks the file, and only Shift gives `⇧V` and `⇧F`. Holding a key repeats only `j` and `k`. `j`, `k`, `v`, `]`, and `[` move the focus to the file or comment they go to; a screen reader hears each command's key.

With **Comment keys** on (under Single-key shortcuts in Settings → Reading), these act on the comment `]` or `[` last landed on, or a row you chose in Comments:

| Key | Action |
|---|---|
| e | Edit it |
| x | Remove it, yours or the agent's, with Undo, except on an older diff |
| 1 / 2 / 3 / 4 | Blocking, Should fix, Question, or Nit, with a toast; a Pre-existing mark stays |
| 0 | Clear its severity |
| r | Reply to the GitHub thread |

A comment on an older diff keeps its severity until you edit it. In a comment box, Cmd/Ctrl+Enter saves and Esc leaves the box with your text in it; the shortcuts sheet lists both.

If you use speech input or press keys by accident, turn off **Single-key shortcuts** in Settings → Reading. Every key above goes, with the hints that name them, and `/` on All reviews too; Esc still closes what's over the code.

With **Commands in BB's command palette** on (Settings → Reading), BB's palette lists **Code Review Workspace: Next review that needs me**, with ⌘⇧U (Ctrl+Shift+U) as its default key unless BB already uses it, **Code Review Workspace: Review PR from clipboard**, which opens the review of the PR link you copied, or starts one and names it ("Started a review of acme/web#7: Fix cache keys") with **Open**, and **Code Review Workspace: All reviews**. Give them keys of your own where BB lets you.

### Phone and iPad

- Every control is a 44px target on a touch screen, iPads included; BB's title-bar buttons are 36px inside 44px targets, and resize handles are 12px wide. The gutter's **+** shows only with a mouse or trackpad; on touch, tap a line, then another for a range.
- On an iPad, the layout is the desktop's at touch sizes, and the band stays while the on-screen keyboard is up. Resizing the window (Split View, Stage Manager, turning the iPad) hides a docked panel that no longer fits, and docks it again when there's room; nothing opens over the code by itself. The band fits its room as with a mouse. Where touch leaves little room, the bars make way: beside docked Comments with under 600px of code, the selection and step bars sit at the code's left. On a 13" iPad held upright with BB's thread list collapsed, docked Comments leaves the code that little room.
- On a phone there's no band. A dock at the bottom holds **‹** (All reviews), the chapter you're on, **Comments** (how many aren't submitted, and a dot when something needs you), **Ask agent**, and **Full screen**. The chapter, Comments, and Ask agent switch one sheet above it between the chapters, Comments with Finish review, and the agent; a flick down, ✕, Esc, its tab, or a tap on the code above it closes the sheet. The chapters sheet holds Diff options and Review actions. The dock steps aside while you type or select lines, and toasts sit above it. Menus open as drawers from the bottom. On All reviews, ⌕ in BB's title bar opens the find box.
- A phone held sideways, or any window under 500px tall, has a 40px band and opens the chapters and panels only over the code, with the chapter intro collapsed. When the on-screen keyboard leaves a phone little room, the band, the notices, the file's sticky row, and Comments' Finish bar step aside for the box you type in, which comes into view with its buttons where they fit, and whole once the keyboard goes away.
- **iPhone 14 Pro Max and iPhone Duo**, held either way, and the Duo folded or unfolded. Folded, the Duo's outer screen gets the phone layout; unfolded, its inner screen gets the tablet layout, with the chapters and Comments beside the code where they fit: held sideways in Safari, Comments docks at 391px beside 560px of code, and in a home-screen app it opens over the code, right of the fold. Folding, unfolding, or turning either phone keeps the line you were reading, what's open (a docked panel becomes the sheet and back), half-typed text with its cursor, Find's text, the lines selected, and the focus, in BB too, which mounts the review anew as its layout switches at a 768px window. ## Whose turn

**All reviews** has four sections, in the order you'll work them. Needs review starts open and the others closed; each remembers what you chose, in this browser.

- **Needs review**: it's your turn. Reviews that came back to you (**Back to you**), new reviews and requests for your review (**New**), and **Team requests**, each longest-waiting first. **Blocks merge** marks a changes-requested review that's the only thing left, since everyone else approved; it comes first. Your own PRs show here as **Your PR** until you've reviewed them, then in Reviewed; they never wait on an author or alert.
- **Waiting on author**: you requested changes, or commented with threads still open, and the author hasn't said they're done. Rows show progress (`2/5 addressed`, `+1 nit`), new commits, CI, outdated threads, and how long the author has been quiet. Snoozed reviews wait here too.
- **Reviewed**: you approved, or commented with every thread resolved or answered. A push after your approval adds “updated” but doesn't bring it back.
- **Archive**: merged, closed, or archived by you; a PR found on GitHub that no longer requests you (**No longer requested**); and one GitHub hasn't found for 7 days (**Can't read on GitHub**).

Each row is two lines: the title, repository and number, and age (in Needs review, how long it's been your turn), then why it's yours and only the facts that change whether to open it, such as the PR's size (`+120 −30 · 8 files`). With a mouse, hovering a row shows **Snooze**, **Pin**, and **Archive**; on touch, every row has its **Review actions** (⋯). The box at the top finds a review, filtering the list by repository, @author, title, or #number, or takes a pasted PR link or `owner/repo#n`: **Open** the review if it's listed, or **Review** it to start one. `/` puts the cursor in the box; on a phone, ⌕ in BB's title bar opens it. The list keeps the box's filter when you come back from a review. **Refresh** and **Settings** sit in BB's title bar; Refresh's tooltip says when GitHub was last read, and the list says why it can't be read now: GitHub CLI not on the BB server, `gh` not signed in, a rate limit (reading then pauses for 15 minutes), or PRs or teams it can't see. Stacked PRs sit together, bottom first, labeled `Stack · 2 of 3`; a review's Overview links **Stacked on #N** and **#N builds on this**, and says when you haven't reviewed the PR below.

BB's thread list shows **Needs review** too, below Pinned and Threads: the same reviews in the same order, with how long each has waited. It collapses like the other groups, and choosing a review opens it. **Pin** a review, from its row there (with a mouse) or its **Review actions** menu, to put it in BB's Pinned group after your pinned threads; it stays until you unpin it or it moves to Archive, and the list marks it with a pin. BB has no plugin slot for any of this, so Code Review Workspace adds it to BB's list itself; if a BB update changes that list, it may not show until Code Review Workspace catches up. To keep BB's list to threads, turn off **Show reviews in the thread list** in Settings; your pins are kept.

A push alone never makes a review your turn: authors often push one fix at a time. A review comes back to **Needs review** when:

- the author **re-requests** your review (it even leaves your archive); a request to a team you're on isn't a re-request;
- the author **asks you something** on one of your threads, or anyone mentions you on the PR, in a review, or in a line comment and you haven't commented since, whatever your verdict (choose **Any reply** in settings to come back on every reply, or turn off **Come back when you're mentioned** to leave mentions out). Only the author's replies count on your threads; anyone else's counts when it @mentions you;
- every thread you opened is **resolved or answered**, apart from non-blocking ones, there are new commits, CI isn't running or failing, and the author has been quiet for 10 minutes;
- with **After the author pushes → Check, and bring it back** on, the review assistant finds all your feedback addressed;
- GitHub dismisses your review.

Once a review comes back because your feedback was handled, it stays in Needs review until you act, even if the author pushes again. Your verdict is your latest approve or changes-requested review, as GitHub counts it: replying to a thread doesn't change it. If a review came back too early, choose **Snooze → Until the author responds** in its **Review actions** menu, its row, or its Overview. It waits on the author until a newer reason; pushes alone don't wake it. Snooze's other choices, **Later today**, **Tomorrow**, **Monday**, and **Pick a date…**, set aside a review or a new request until then (between midnight and 9 AM, Pick a date can choose this morning): it waits as "Snoozed until Mon 9:00 AM" and comes back at that time, with a Needs You alert, or sooner for a newer reason, which alerts then and not again at the snooze's time. **Back to Needs review** ends a snooze. Snooze, Pin, and Archive can be undone from their toast.

A thread whose first comment starts with `nit:`, `FYI:`, `optional:`, or `non-blocking:` (bold or not) is **non-blocking**. It doesn't keep a review on the author, progress counts it apart (`2/2 handled +1 nit`), and Request what's left leaves it out; a question on it still brings the review back. Comments you submit with the **Nit** severity start that way, pre-existing ones too.

Code Review Workspace alerts only about what happens after it starts following a PR: after an upgrade, or when it first finds PRs on GitHub, the list fills in quietly, except new requests for your review.

**When a review comes back, it's prepared for you.** An out-of-date guide is rebuilt for the new commits, keeping its chapters where the files still fit and summarizing what changed since your review; if the rebuild fails, the previous guide stays. (For a PR found on GitHub, without a guide of its own, this happens only in your auto-start repositories.) Then the review assistant checks your feedback, in the review's own conversation: for each of your threads, and each ask in your review summary, it records whether the author **addressed** it, partly, not at all, or disagreed, with one line of evidence. It also looks for new problems in the fix commits, drafts replies to your threads, and suggests a verdict with a summary, which goes into your draft. Comments shows all of it. The agent's check sits at the top ("Agent’s check · a1b2c3d · 2h · 2 of 3 addressed", with **Check again**), and **Needs you** lists each thread that needs you, non-blocking ones last: your comment, the author's replies, the assistant's verdict and evidence (**Show the fix** opens its line), the drafted reply waiting as an "Agent reply draft · not sent", **Reply**, **Resolve**, and in ⋯ **Follow up** (a new draft comment at the line). Your feedback's progress on the Overview opens it. If you'd already written your own summary, the suggestion waits in **Finish review**: **Use as draft** puts it and its verdict in your draft. **Request what's left** drafts a Request changes listing what's still open. Nothing posts to GitHub until you choose Send reply, Resolve, or Submit. **Get a review ready before alerting you**, on by default, holds the alert for this, at most 10 minutes; off, the alert comes at once, and **Update guide** and **Check again** are a click away. Change the check's instructions with **Re-review check** in settings, or turn it off with **Run the re-review check**, which keeps them.

On a re-review, the diff opens on what changed since your review, however you get to a chapter: Review changes, Continue, a chapter you pick, or a comment. To open on the whole PR instead, choose **All changes** under **Settings → Re-reviews**. A switch in each chapter's intro flips between the two in one tap, on every device, and says how many of the chapter's files changed: "Since your review · 1 of 3 files | All changes". A chapter with nothing new says "Nothing changed in this chapter since your review". **Since your review** shows only what changed since the commit you last reviewed, with new lines marked. It compares the PR's diff then with its diff now, so rebases and merges from the base branch don't show up as changes, and a diff that didn't change, as after a rebase, opens on all of it. Viewed marks survive a rebase, and chapters show how many of their files changed. The compare select in the band says what the diff shows too: **All changes**, **Since your review**, or since a commit. Its menu lists your last review, then the PR's earlier commits: pick one to see what changed since it ("Since abc1234"). On a PR you haven't reviewed, **Compare with a commit…** in Diff options does the same. Where the band has no room for the select, Diff options holds the comparison. A comparison that fails says why. What you choose holds for that review in this browser, a picked commit too, until the author pushes and its guide updates; then it opens on your Settings choice again. Opening a file or a line the comparison hides, from the chapters, a comment, or a Find result, shows all changes, and that holds too.

With **Track reviews from GitHub** on (the default), PRs where your review is requested, and open PRs you've reviewed that changed in the last 60 days (unless **Include PRs you've reviewed** is off), join the list without a guide; build one with **Build the guide** on its page or in its menu. Requests to a team you're on join only with **Include team requests**: teams can be asked for many reviews. Turning on either switch fills the list with what it finds already there, without starting guides or alerting. List patterns under **Start guides automatically** (`acme/*`, `acme/api`, or `*`) to have the guide ready by the time a request alerts you. A PR you delete isn't added back. Reading GitHub costs about 6 GraphQL points per 10 PRs a pass, plus about 2 points to re-read the threads of an active review with an open thread of yours, every 10 minutes, out of the 5,000 an hour your account has.

## Customize your reviews

Open **Settings** from ⚙ in BB's title bar on All reviews, or **Review settings…** in a review's ⋯ menu, or use Code Review Workspace’s section in BB’s plugin settings. Its page goes back where you opened it from: **All reviews** or **Back to review**. Its sections: **Ready to review** (your GitHub account and its switcher), **Plugin updates**, **Notifications**, **Guide generation** (Concise, Standard, or Detailed guides, guide-writing instructions, and Stop), **Review agent** (its priorities and prompts), **Whose turn** (how reviews come back to you), **Re-reviews** (what a re-review opens on: what changed since your review, or all changes), **Reading**, **Comments and Finish review**, **BB's thread list**, and **Trust** (who agents run for on their own; see [Data and access](#data-and-access)). Save settings to apply them across this installation. Restore defaults stages a change for you to save; it does not change settings immediately. The diff's layout is set in a review's Diff options, for every review.

These switches turn a feature off; each is on by default. A setting that depends on another is indented, and disabled while that one is off.

**Flag chapters read faster than** sets Check before you approve's pace: 100 to 2,000 lines an hour, 500 by default. If settings are slow or can't load, a review opens after about a second with the switches this browser last loaded, and takes your settings when they arrive; a browser that never loaded them uses the defaults.

Guide instructions extend the bundled `code-review-workspace-generate` skill. They apply to new guides and to guides you update or rebuild; the output schema and complete file coverage remain validated. Assistant instructions, up to 2,000 characters, reach the assistant as hidden instructions; an idle conversation picks up changes on its next message. **Automatic review** is the assistant's first message when a guide is ready and the review has no conversation yet. By default it asks for a precision-first review: at most 10 comments, each confirmed in the code, with a note of how, and labeled with its severity, and a review summary with the verdict it suggests by stated rules. On your own PR it's a self-review that suggests Comment. Settings saved with an earlier default use the new one. Turn off **Run the automatic review** to stop it and keep the prompt; leaving the prompt blank stops it too.

The assistant learns from what you remove. When you remove a comment it wrote, it's told not to raise it again unless the code changes. **Comment removed** offers **Why?** for an agent's comment: **Wrong**, **Intended**, **Already known**, or **Not worth it**, in one tap, with an optional note; choosing it closes the toast and its Undo. The agent sees your reason, and your note as data rather than instructions, and Settings splits the removals ("Removed 6: 3 wrong, 2 not worth it, 1 intended"). Each submitted review records whether you kept, edited, or removed each of its comments, and Settings shows the tally ("Of the agent's last 40 comments you kept 31 as written, edited 6, removed 3") with the comments you removed lately. **Suggest instruction changes** asks the agent for up to five instruction lines from those removed and edited comments, and your reasons; you edit them, add them to Assistant instructions, and nothing applies until you save.

The guide writer and the review assistant each have an **Agent** setting. **Project defaults** runs on the BB server with the provider, model, and reasoning effort BB remembers for the review’s project. The review assistant takes the project’s permission mode too; the hidden guide writer, which needs no shell or edits, runs at the lowest mode its provider runs in: Accept Edits, else Auto, else the project’s. **Custom** pins all four, plus the service tier where the provider has one, with BB’s pickers, starting from the Personal project’s defaults, with the guide writer at Accept Edits, else Auto, else the provider’s only mode (Accept Edits when the defaults can’t be read). A provider that runs only at Full, as pi does, can’t restrict its agent, and Settings says so under the picker, naming the providers that run at Accept Edits. Any reasoning level a provider offers can be saved. Custom also chooses the **Machine**: the BB server or another enrolled machine, such as your laptop. The pickers then list that machine’s providers, models, and permission limit, and the agent runs in its Personal workspace with the agent configuration installed there; within the chosen permission mode, it can reach that machine’s files and credentials. If the machine is offline or removed, building, updating, or rebuilding a guide, `bb review`, and a new assistant conversation fail at once and say why. Guide-writer changes apply to new guides and to guides you update or rebuild. The review assistant’s setting seeds the agent picker for a new conversation; within a conversation, change the model and effort per message as in any BB chat. A conversation keeps its provider and machine; to switch, start a **New conversation**. If BB can’t start a custom agent (for example, its provider was disabled), the assistant shows the error; failed generation records it in the plugin log.

## Comments and Finish review

**Comments** (`c`, or **Comments** in BB's title bar) lists everything said about the change, beside the code, never instead of it: your draft comments and the agent's, everyone's GitHub threads, and your discussions with the agent. Its chips, **All**, **Needs you**, **Not submitted**, and **On GitHub**, show a count each and filter the list; on a touch screen they wrap to a second row where they don't fit. The list is grouped in that order: **Needs you** (a question for you, an author's reply, a thread the agent's check says isn't addressed, an agent reply draft, a comment on an older diff), **Not submitted · only in BB** (counted by severity, "1 blocking · 2 nits"), **On GitHub** (yours first, "Yours: 2 of 2 handled +1 nit", then other people's; resolved and outdated threads folded), and **Private · with the agent**, in reading order within each. Choosing a row shows its comment in the code, switching chapter and unfolding it if needed; its ⌄ opens the whole card in place, which is how file comments, outdated threads, and asks from your review summary read. ↻ reads GitHub again. ⋯ **Comment options** holds **Hide nits** (remembered in this browser, in the code too), **Remove nits**, **Show resolved threads**, **Add comment by line…**, and **Open PR on GitHub**. While you write a comment in the code, the list says where, with **Show in diff**. Comments on a local review stay in BB.

Every comment is the same card in Comments and in the code, and says where it lives, in words as well as looks. Anything only in BB is dashed and says so: "Draft · not submitted", "Agent draft · not submitted" for one an agent wrote, until you edit it, and "Older diff · not submitted". A GitHub thread is solid, headed **On GitHub**, with who wrote each comment and when, who resolved it, and its state: "Waiting on author", "Author replied", "Question for you", "Resolved", "Outdated", or "File comment". A discussion with the agent is muted, with a lock: "Private · with the agent". `]` and `[` step through the list's current chip, across chapters; with Comments closed, a hint says where you are ("2 of 5 · Not submitted"), and on touch, after you open a comment from the list, a step bar does.

Each line comment can have a severity: **Blocking**, **Should fix**, **Question**, or **Nit**. Set it in the comment box, or start the comment with its label, such as `**Blocking:**`; the card shows it, and GitHub gets the label in front of the comment. Removing a comment shows a toast with **Undo**, which puts it back on the diff it was removed from; after a guide update, it says why it can't. Changes from the assistant or `bb review comment` appear in Comments and the code as they happen. Agents can also edit and delete comments, and are told to change yours only when you ask. Nothing they do posts to GitHub.

With **Keep pre-existing problems apart** on, the agent marks a problem in code the PR didn't change, and its card says **Pre-existing**, beside the severity. **Mark as pre-existing** and **Mark as from this PR** in a draft's card change it. A pre-existing comment doesn't count as blocking against Approve, Not submitted counts it apart ("· 1 pre-existing"), and it posts with "**Pre-existing:**" in front, as it does when you move it to the summary or send it to a coding thread.

What you write in a reply, on anyone's GitHub thread, waits as a reply draft ("Reply draft · not sent") until **Send reply** posts it, at once, not with your review; **Discard** drops it. **Resolve** posts at once too, and says so. Both post as the GitHub account the review verified, and wait until it has. A reply or resolve in the code shows in the list at once, and the other way round.

**Finish review** (`s`, **Finish review** in BB's title bar, or the bar at Comments' foot, which says the verdict and how many comments will be sent; a phone's dock says "2 to send") holds what goes to GitHub when you submit: the summary, the verdict, and exactly what will be posted.

- **Summary · posted with your verdict:** the comment GitHub shows with your verdict, above the line comments. It works like a line comment. The assistant writes it, labeled "Agent summary · not submitted", and suggests a verdict; only you pick the verdict. **Edit** makes the summary yours, and **Remove** clears it. **Ask agent** opens a discussion with the assistant under the summary: ask why, or say what to change, and the assistant changes the summary there. **Undo** puts back its latest change. The assistant never replaces a summary you wrote unless you ask on it, and then only while it answers that ask, not in work it was already doing. While it works on the summary, Edit waits; if the summary changes while you're editing it, the box says so before you save. When a summary the assistant wrote no longer fits your comments, or the verdict you picked, it says so, with **Update**. With no summary, **Write summary** or **Ask agent to write it**. Since Move to summary can put an agent's words in it, the card shows any summary's images as links, yours too; GitHub gets it as written.
- **Verdict:** Approve, Comment, or Request changes, the agent's suggestion marked with a sparkle. "Agent suggests …" shows its suggested summary, or its check's, with **Use as draft**, **Request what's left**, and, when you picked another verdict, **Switch to** it. Beside it, Finish review says how many of the changed files the agent read as the change leaves them ("Read 6 of 8 files", lockfiles and generated files aside) and folds **What it didn't check**, as the agent wrote it (unless **Show what the agent checked** is off). On your own PR only Comment is offered, as GitHub refuses the others.
- **Goes to GitHub:** the comments and their severities, and anything to settle first, each with its fix: comments on an older diff (Submit waits until you edit and save them, remove them, or **Move to summary**), a Request changes without a summary (it waits for one), a verdict other than the agent's, or an approval with blocking comments. While you approve, it also flags files in high-risk chapters you haven't viewed ("2 files in high-risk chapters not viewed", with **Show**), and each medium- or high-risk chapter of 50 lines or more marked viewed faster than anyone reads ("Chapter 2 (high risk): 1,200 lines marked viewed in 3 min", past 500 lines an hour); lockfiles and generated files don't count. **Check before you approve** in Settings turns these off, and sets the pace. When the agent suggests Approve but didn't read every changed file, a row says so ("The agent suggests Approve but read 6 of 8 files", with **Show**). Pre-existing comments are counted apart. Reply drafts are listed too: they post on their own, with Send reply.
- **Stays in BB:** **Private notes**, only if you have some (see below).
- **Submit to GitHub**, with your verdict on it ("Submit to GitHub · Approve · 1 blocking"), pinned at the foot, with where it posts and as whom. It asks once more (**Submit anyway**) when the verdict isn't the one the agent suggested, the agent's summary is out of date, or you approve with blocking comments, high-risk files not viewed, chapters read too fast, or files the agent didn't read; otherwise it's one click. It reads **Submitting…** while it posts, and waits while you're writing a comment or the summary. Submit refuses a draft whose comments, summary, or verdict changed since the page last showed them, or a page that doesn't send them. If GitHub's answer is lost or doesn't come within 5 minutes, Submit looks on GitHub for the review it just posted and finishes with it, rather than post it twice; if it can't check, it says to look at the PR before submitting again. If you started a pending review on github.com, Submit says to submit or discard it there, then submit again.

After you submit, the panel reads **Review submitted**: the verdict, where it posted and as whom, **View on GitHub**, **Add another review**, and the next review in Needs review, with **Open**. A merged or closed PR's Comments ends with "Merged · Archived" and **Open**: its **Archived review**, with the unsubmitted draft and notes to read.

On your own PR or a local review, **Fix in a new thread**, in Finish review, hands the draft comments you choose to a visible BB thread in the review's project. Its first message lists each comment with its file, lines, severity, and code, and the branch and commit you reviewed. It runs on the review assistant's Agent setting, and is told not to push or change GitHub unless you ask in that thread. The draft isn't changed or submitted.

When you started the review with `bb review` in a thread, Finish review leads instead with **Send N comments to ‹thread›**, the thread that made the change, with "or Fix in a new thread" beside it. It sends only on your click, with the same picker and message, queued behind whatever that thread is doing, and asks it to reply with what it changed; nothing goes to GitHub. Then it says "Sent to ‹thread›" or "Queued in ‹thread›", with **Open**, and each comment you sent says "Sent to ‹thread› · 2m" on its card, still not submitted, until you edit it. If that thread was archived or deleted, only Fix in a new thread is offered, and Finish review says why. **Send comments to the thread that made the change** in Settings turns it off.

Reviewer notes are no longer a tool. Notes you wrote before 0.6.0 are under Finish review → Stays in BB → **Private notes**, only when you have some: saved in BB, and never included in GitHub submissions or assistant prompts. Notes survive submission and archival. If saving fails, unsaved notes have a browser recovery copy; conflicting edits can be compared with the saved version before choosing what to keep. Existing review summaries retain their original public-draft meaning, and count as yours.

## Data and access

Review metadata, patches, generated guides, and drafts are stored in this BB installation’s plugin database. Review agents receive the patch and context through your configured BB provider; that provider’s data handling applies. The review assistant runs in the permission mode of its Agent setting, on a machine whose `gh` login can usually write to GitHub. Its instructions forbid GitHub writes, but text in a PR could try to steer it, and the automatic review runs unattended; choose its permission mode with that in mind. The guide writer runs hidden and unattended too, using only Code Review Workspace's tools and one that reads a linked ticket; on Project defaults it runs at Accept Edits where its provider allows (see [Customize your reviews](#customize-your-reviews)). Claude Code, Codex, and OpenCode run at Accept Edits; pi runs only at Full, so an agent on pi runs at Full and can't be restricted, and Settings says so. The agents follow ticket references only in a trusted author's PR, and only ever read tickets: never write to an issue tracker or chat, or quote a private ticket into a draft. What agents write for GitHub is capped at 65,000 characters. This plugin does not add a separate hosted review service.

The assistant and the guide writer read only their own review's diff and PR context, and get their tools by the role the plugin recorded for their thread, whatever their thread is renamed to or its metadata says. One brief window remains: while a review's assistant or guide writer is being started, typically well under a second, another of this plugin's threads titled exactly as the new one would count as it. A review's assistant and guide writer can't use `bb review`, `bb review comment`, or `bb review summary` on another review, and a guide one starts on its own review doesn't count as your click. Neither can an assistant that New conversation replaced or found archived, nor an earlier guide writer, one a reload interrupted included, nor a review's thread that deleting the review couldn't stop or delete, and the **Suggest instruction changes** worker can't use them on any review. `bb review` on a PR from one of your other BB threads counts as your click only for an author agents run for on their own (see below), and with **Start agents on their own** off only on your own PR; for anyone else, or when GitHub can't say, it builds the guide and leaves the run to your click. These limits hold for agents running `bb review` as BB starts it in their thread: BB tells the plugin which thread runs a command, and an agent with a shell can hide that. An agent with a shell in another thread can still run `bb review` commands on any review, and change Settings through the plugin's calls, as the panel does.

The agents read the repository's instructions (AGENTS.md, CLAUDE.md, `.github/copilot-instructions.md`, `.github/instructions`, and with **Read REVIEW.md** on, REVIEW.md at the root and in the changed files' directories and those above them) from the PR's base, or a local diff's start, never from the PR's head, and are told when the PR changes them. Which files are generated, from `.gitattributes`, is read at the PR's merge base too, so a PR can't fold its own code. The agents read a big diff in 80 KB pages, with lockfiles and generated and vendored files as one-line stubs that name a lockfile's new download hosts, in every lockfile format but go.sum, which holds no URLs, apart from its public registries (github.com counts as one for composer and Swift packages), and with a `\` ending a URL's host as package managers read it; a file the PR adds is always read in full. They're told when GitHub's 3,000-file list may have cut a huge PR short, and which files GitHub sent no diff for. Commit headlines, the earlier guide's chapters, CI logs, `bb review --context`, and your removal notes reach them fenced as untrusted text, and a changed path holding a line break or other control character is quoted. In other people's GitHub comments, the guide, CI annotations, the agents' words, and the review summary, images, named by their alt text, and videos show as links; HTML comments are hidden, as GitHub hides them; and other HTML shows as text, but for a few tags that only format (such as `details`, `summary`, `p`, `b`, `kbd`, lists, and tables, with attributes such as `open` and `align` only). Code spans and fenced code, in table cells too, show as written where the plugin can tell they're code. Where it can't tell code from text, as inside an HTML block, after `$$` math or a footnote, or in a code span that a table's pipe splits, it treats the code as text: a `<` in it shows as `&lt;`, and an image as a link.

The automatic review never starts on a PR already merged or closed. So agents start on their own (an auto-started guide, the automatic review, the feedback check) only on PRs from the repository's owner, members, and collaborators, and only when the PR's branch isn't in someone else's fork, whose owner can push to it. Change who under **Settings → Trust → Run agents on their own for PRs from**: members and collaborators (the default), or anyone, which lets a fork's branch run too. Turn off **Start agents on their own** to have other people's PRs wait for your click whoever wrote them; skipped runs then say "Start agents on their own is off in Settings". Your own PRs and local reviews always run, unless the PR's branch is in someone else's fork. On another author's PR, the list row and the review say what didn't run and why ("Not run automatically: @x isn’t a member of acme"), and the review offers one click to run it. An automatic review that couldn't start, as when its agent's machine is offline, says so and why ("Not run automatically: it couldn’t start (…)"), with **Run review** to try again; nothing retries on its own. **Run review** on a review whose conversation is under way sends the automatic review there. With **Run the automatic review** off, or on a merged or closed PR, **Run review** says why it can't run, and **Run check** does with **Run the re-review check** off; the notice stays. A run you start lets the automatic review and checks on that commit follow; each new push needs a new click, and so does an edit to the PR's title or description by an outside author after your click. A click from 0.7.0 on a PR edited since needs one more. Once you turn Start agents on their own back on, a run skipped while it was off says "Not run automatically: Start agents on their own was off in Settings when this came in".

**Let the review agent run the repo’s tests and linters**, off by default, lets the review agent run the commands the repository documents, in a temporary git worktree. **This runs the PR's code on the agent's machine**, with that machine's files and credentials in reach. It applies only to your own PRs and PRs from the authors you trust above, never to a branch in someone else's fork unless you trust anyone, and a click never allows it for others. With Start agents on their own off, the authors setting still decides whose PRs it runs on. With **Anyone** and this both on, Trust warns: "With Anyone, this runs code from any GitHub user’s PR, forks included, on this server, where gh is signed in."

**Ask agent** on an Overview's failing check runs `gh run view --log-failed` to read that check's log, only on that click; it writes nothing.

Reviews of PRs merged or closed for 30 days drop their stored diff to save space; the guide, draft, and notes stay, and opening one reads the diff from GitHub again. Open PRs, local reviews, guides for an earlier head, and drafts with comments keep theirs.

GitHub operations use the server’s `gh` credentials. No token needs to be pasted into the plugin. Replies, resolves, and unresolves post as the account the review verified, only on the review's own PR's threads; a page from 0.7.0 is asked to reload first. Switching the account switches `gh` for everything on the BB server, other agents and terminals included, and the account menu says so. Switching starts each review afresh for the new account: its feedback check, held turn, click, skipped run, and alerts. Grant only the repository access your team needs. A shared BB server uses shared server credentials and plugin storage; it is not a multi-tenant review service.

Older saved reviews remain available. New reviews use repository-scoped identifiers, preventing equal PR numbers in different repositories from overwriting each other. Legacy inline drafts must be removed and re-added against the current patch before submission.

## Development

```sh
npm ci
bb plugin types
npm run check
bb plugin install .
bb plugin dev
```

Development checks use the SDK test harness, temporary Git repositories, and mocked GitHub writes. A backend test that runs the real `gh` fails: a stand-in `gh` goes first on `PATH`. Frontend tests are collected from `components/`, `lib/`, and `hooks/`, in `.ts` or `.tsx`. `npm run typecheck` covers the server's tests, the browser tests, and the vitest config too. The plugin builds and tests against the SDK the host runs (0.6.49), and uses only what the SDK floor, 0.6.14, has. Use a Node.js version compatible with the installed `better-sqlite3` package (this release was verified on Node.js 24).

BB builds the plugin from source when it installs or updates it, so the build output in `dist/` isn't committed. Keep published tags immutable. Read [CHANGELOG.md](CHANGELOG.md) for release changes.

## Review state and archive

Each review’s assistant conversation is a hidden BB thread, shown in the review with BB’s chat. Review context (guide intent, chapters, and your assistant instructions) reaches it as hidden instructions, refreshed when an idle conversation continues after the guide is updated or rebuilt, or the instructions change. Selections and the Ask agent button quote the file or lines into your message. **New conversation** archives the current one; if a conversation’s thread is archived or deleted, the next question starts a new one. Archived PRs can still be discussed: their conversations stay unarchived because BB cannot send to an archived thread. A conversation from an earlier plugin version stays visible above the chat and reaches the first new message as context. A guide writer that stops without a guide the plugin accepts is reminded once; a guide that still fails says why under **What went wrong**, and the plugin log keeps it. **Stop**, on the building screen or a guide update's notice, stops the guide writer: an update goes back to the guide you had ("Stopped. The guide is as it was."), and a first guide says "Guide stopped", in its status line too, with **Build the guide**, on a merged or closed PR too. A guide a reload interrupted restarts once its writer's machine reconnects, for up to 10 minutes; meanwhile its page and its status line say "Waiting for the guide writer's machine", and its update notice says "The guide writer's machine is offline. The update restarts on its own when it reconnects.", the page and the notice with **Try again**. After that it reads as failed, and says why under What went wrong, as does one whose restart failed, as when GitHub couldn't be read. Where a submitted review appears depends on whose turn it is; see [Whose turn](#whose-turn). Merged and closed PRs move to Archive automatically; their guides, conversations, and unsent drafts remain accessible. GitHub is checked every one to two minutes for reviews in progress, sooner when GitHub notifies you about a PR, and through Refresh. A failed GitHub read preserves saved state.

To set aside any other review, choose **Archive** from its **Review actions** menu (⋯) in All reviews or the review’s title bar. It stays in Archive, even when new commits arrive, until you choose **Unarchive**, start it again with `bb review`, update or rebuild its guide, or the author re-requests your review. **Delete** permanently removes the review’s guide, drafts, private notes, and assistant conversation, including its hidden worker threads and guide writers, after confirmation, and this browser forgets where you left it and its agent dock; nothing changes on GitHub. Delete is unavailable while a guide is generating or the assistant is answering. A deleted PR isn't added back from GitHub until you start it again.

## Browser regression test

Use Node 24, matching the installed SQLite native module. Build and reload this plugin in an isolated test BB, then run:

```sh
npm install
npx playwright install chromium
bb plugin build
BB_SERVER_URL=http://127.0.0.1:4331 bb plugin reload code-review-workspace
BB_E2E_URL=http://127.0.0.1:4331 npm test -- --project e2e
```

`BB_E2E_URL` must point at a BB on this machine (`127.0.0.1`, `localhost`, or `[::1]`): the test writes reviews and settings to the BB it reaches.

The browser uses the running BB shell and built plugin UI. Code Review Workspace RPC requests are intercepted into the official SDK test host with real temporary SQLite. GitHub and agent calls are stubbed at their external boundaries, so no real PR review or agent thread is created. The flow covers settings persistence, the Overview and Start reading, Comments from BB's title bar and its state across a reload, adding a comment by line and editing it in the code, keyboard tooltips, Finish review's summary, verdict, and private notes, Finish in a 390px phone's Comments sheet above the dock, full screen's verdict and Submit, reload, starting an assistant conversation with file context, Pop out and Dock keeping a half-typed message, All reviews' sections, and merge archival. Without `BB_E2E_URL`, this test is skipped.

A second browser test checks Needs You notifications: a finished guide's popup, opening the review from it, the retained inbox row, and Dismiss. It needs a separate isolated test BB on port 4333 with Needs You installed, and saves a screenshot to `docs/verification/` (gitignored):

```sh
BB_ACTIVITY_E2E_URL=http://127.0.0.1:4333 npm test -- --project e2e
```

Without `BB_ACTIVITY_E2E_URL`, it is skipped.


## Notifications

With **Needs You 0.2.0-beta.3+** installed, a finished guide appears in your Needs
You inbox with an **Open review** action. Failed generation has its own recovery
message. A review becoming your turn alerts too: re-requested, a request for your
review, a question for you or a mention, your feedback handled, or a timed snooze
ending. Each event alerts once. **Settings → Notifications** turns off either kind:
**A guide is ready or failed**, or **A review becomes your turn**. When Code Review Workspace prepares the re-review first, the alert waits for it (at most
10 minutes, unless **Get a review ready before alerting you** is off) and says how much of your feedback was addressed, for example
`@alice re-requested your review · 4/5 addressed · CI passing · 2 new commits`.
Opening the review, submitting, or snoozing it clears the alert.
Each review has one inbox item; hidden worker threads do not create extra alerts. Enable **Needs You → Settings → Extension activity** to receive
popups, desktop alerts, or optional Telegram pushes through your chosen channels.
Quiet hours apply, and a popup stays quiet while you are already viewing that guide.

Needs You is optional. If it is disabled, missing, or restarting, Code Review Workspace
keeps the guide successful and retries the same completion event once a minute
for up to 24 hours while loaded. Restarting preserves queued outcomes. A newer
generation supersedes the previous queued result; cancelled workers never ping.
